01

Nothing gets uploaded

Processing happens in this browser. Meta-Stripper does not send the selected image, filenames, metadata or results to a server. There are no third-party scripts or trackers.

02

Pixels are re-encoded

The browser decodes the image, draws the visible pixels to a canvas, then creates a new file. The source container and its metadata blocks are not copied into the export.

03

The export is checked

The new file is scanned locally for known source-metadata markers, including EXIF, XMP, IPTC and common embedded C2PA/JUMBF locations. If a known source marker remains, download is blocked.

Reality check

What this can — and cannot — promise

It can

  • Remove source EXIF, GPS, XMP and IPTC metadata by re-encoding.
  • Remove embedded JPEG APP11 / PNG caBX C2PA/JUMBF data when re-encoding succeeds.
  • Verify that known embedded source-metadata markers are absent from the new file.
  • Operate without uploading your image anywhere.

It cannot guarantee

  • That every platform will display no CR/C2PA indicator now or in the future.
  • That a platform cannot match the pixels through a perceptual fingerprint.
  • That an invisible watermark embedded in the pixels cannot be recovered.
  • That browser-generated technical encoding data is literally zero bytes of metadata.

Meta-Stripper does not modify pixels to defeat invisible watermarks or provenance-recovery systems. C2PA supports “soft bindings” such as fingerprints and invisible watermarks that can reconnect a derived image to external provenance data even after an embedded manifest has been removed.
